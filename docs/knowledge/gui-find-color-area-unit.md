# find_color 的 min_pixels 曾经错杀小目标: 面积换算的 unit 写错了

## 现象

在画图上做坐标校准的回测时, 想用 `vision.find_color` 找色板上的彩色方块
(标准色 `(237,28,36)` 之类), 结果**一个彩色块都找不到**, 反而是"黑色"命中了
画布上一条 186x165 的大笔迹。采样明明显示 `(640, 45)` 处的像素就是
`(237, 33, 41)` —— 与目标色只差切比雪夫距离 5, 远小于 tol=36。

## 为什么

`find_color` 的流程是: 稀疏采样命中点 → 落进 `cell` 大小的格子去重 → 聚成簇 →
`approx = count × unit` 与 `min_pixels` 比较决定去留。问题出在 unit:

- `hits` 是**去重后的格数**。一格代表 `cell²` 个像素 (默认 6² = 36);
- 但代码写的是 `unit = step * step` (默认 2² = 4), 低估了 (cell/step)² = 9 倍。

色板方块真实 12px, 截图缩放 0.76 倍后剩 ~9px, 纯色核心更小 —— 聚簇后只有
十来个格, 乘 4 之后连 `min_pixels=25` 都过不了。**任何小于 ~60/9 ≈ 7 格的目标
都会被 min_pixels 错杀**, 而"找小图标/小色块"恰恰是按颜色定位最常见的场景。

大目标为什么没事? 40x20 的块有 ~20 格, 乘 4 是 80, 勉强过 60 —— 这也是为什么
单看测试发现不了: 测试里的"大块"刚好够大, "碎屑"刚好被判对, bug 藏在中间地带。

## 修法

```python
approx = min(count * cell * cell, (x1 - x0) * (y1 - y0))
```

- 乘 `cell²` 才是每格代表的近似面积;
- 再拿**格子的外接盒面积**封顶 —— 只占一格的碎屑会被高估成 36px, 封顶之后
  它的 `approx` 就是外接盒本身, 小于 min_pixels 照样滤掉, "丢碎屑"的语义不丢。

注意粒度限制没变: 占不满一格的目标 (<= 6px) 与跨 1 格的目标在格坐标上分不开,
`find_color` 从来就不是精确面积的工具 —— 文档里写了"取 center 点按钮没问题,
拿来算精确面积不合适"。修的是**数量级**, 不是精度。

## 教训

- **过滤阈值类参数的语义, 要用"真实世界的最小目标"校一遍**: 单元测试里的大块
  (40x20) 比真机目标 (12px 色块) 大一个数量级, 阈值错 9 倍照样全绿。
- 测试断言"10x10 的碎屑应被 min_pixels=60 滤掉"其实是把语义搞反了 —— 100 真实
  像素本就不该被 60 滤掉, 它只是被错误的换算错杀了。修 bug 时要把这类"错着也能
  自圆其说"的断言一起纠正, 不然 bug 会被测试保护着。
