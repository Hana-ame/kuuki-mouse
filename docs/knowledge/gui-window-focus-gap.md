# locate 之前, 先确认你操作的是哪个窗口

## 现象

一次"用 repo 纯视觉能力在 Gemini 里发消息"的端到端脚本, 每一步都"成功"了:

- 在屏幕顶部找到一排 18px 高饱和小图标, 间隔 54px —— 判定为"浏览器标签栏";
- 逐个点击并用帧差验证"切换生效";
- 找到浅色空白块点击后帧差出现聚焦反馈 —— 判定为"输入框";
- 粘贴文本成功, diff 出现 4 处变化。

但最后对照截图一看: **整个流程点在了 WorkBuddy 自己的窗口上**。
那排"favicon"是 WorkBuddy 的会话标签栏, "输入框"是 WorkBuddy 的聊天输入框,
粘贴的文字落进了 WorkBuddy。没有造成事故(没发送出去、输入框是空的), 纯属走运。

## 为什么

纯视觉定位有**语义天花板**: 一排彩色小图标 + 浅色界面, 浏览器标签栏和
WorkBuddy 的会话标签栏长的一样; 一个"点一下会高亮的框", 聊天输入框和搜索框
也没有本质区别。视觉只能告诉你"这里有个像输入框的东西", 不能告诉你
"这是不是你想操作的那个应用"。

关键缺失的一环是**前台窗口不可知**: 受控端没有 window.list / window.focus,
调用方不知道当前最前面的窗口是谁, 只能假设 —— 而这个假设在桌面多窗口环境下
必然猜错一次。

## 怎么避开

1. 在跑任何"视觉定位 + 点击"的流程**之前**, 先截一帧全屏确认前台是谁
   (哪怕人工瞄一眼) —— 这是目前唯一的兜底。
2. 需要可靠的窗口切换时, 必须先补 window 类 op (见 `todo-open-items.md`),
   用标题/进程名匹配而不是猜坐标。
3. 视觉自举里要保留**否证手段**: 粘贴前后 diff 的变化区域必须覆盖目标点,
   不覆盖就说明焦点不在那里, 立即中止而不是继续发。
4. 探索性的点击永远先点"无副作用"的位置(空白块、输入框), 把 type/paste
   放在聚焦确认之后 —— 本次的 paste 幸好没有落到 Edge 的聊天框里。
