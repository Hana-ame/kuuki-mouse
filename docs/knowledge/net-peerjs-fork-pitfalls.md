# peerjs fork 的两个坑（不归我们，但影响判断）

用的 PeerJS 是本仓库的 fork，它有两个问题我们绕不开：

1. **`_tryBuffer()` 里 `self._trySend(msg)` 是协程却没 `await`** —— 一旦触发背压，
   buffer 里的消息会被当成「已发送」直接丢掉。**缓解：别依赖它的内部缓冲**，
   send 之前确认 `conn.open`
2. **`__peerData` 的库内分块被注释掉了** —— 所以 8KB 的**应用层分块是我们自己必须
   做的**，不是优化

## 由第 2 条决定的协议长相

- 只能 JSON 序列化，图片走 base64
- 自己做的 8KB 应用层分块，**大于 60KB 才分**（小图直接一帧发完）
- batch 必须在**信封顶层**，不能塞进某条消息内部

改协议前先确认这些约束还在不在 —— 它们看起来像过度设计，其实是被 fork 的性质逼出来的。
